# Computer Use 统一到 cua-driver：决策记录

配套设计文档：[cua-driver-tech-design.md](cua-driver-tech-design.md)。这里只记录有取舍的决定，其余结论直接写在设计文档的对应章节里。

## ADR-0001：固定安装版本，已有安装以 0.34.0 为最低版本

- **状态**：已接受（2026-10-15），同日按源码对照审查修订
- **背景**：
  - cua-driver 更新很快，几天就发一版，GitHub 上 `cua-driver-rs-v*` 的版本都标为预发布。它自带 `update --apply` 和 stable/nightly 渠道。
  - macOS 上 cua-driver 只有一份全机共用的安装（`/Applications/CuaDriver.app`）和一个共用的守护进程。用户自己或其他工具随时可能升级它；`cua-driver mcp` 启动时也会提示有新版本。
  - 官方安装器覆盖已有安装时，会结束所有正在运行的守护进程；签名要求变化时，还会清除已有授权（`_install-rust.sh` 0.34.0，约第 196–253、1492–1505 行）。
- **决定**：
  - DreamCoder **自己安装时**固定安装 **0.34.0**，即维护者当前在 stable 渠道上实际使用、体验过的版本。DreamCoder 不调用 cua 的自动升级。升级只通过修改 `CUA_DRIVER_VERSION` 完成，每次升级前在 macOS 上手动回归，并同步检查只读工具名单和工具显示映射。
  - **检测已有安装时**，0.34.0 是最低版本：不低于它就直接使用，更高时只给提示；低于它时，经确认才安装 0.34.0。不提供降级。
- **取舍**：
  - **好处**：我们自己装的版本行为可预期，问题能复现。如果 cua 停止维护或修改许可证，我们可以停在已验证的版本。不会为了版本相等而降级用户的共用安装，打断用户的其他工具。
  - **代价**：
    - 用户拿不到 cua 的最新修复，需要我们主动跟进版本。
    - macOS 上实际运行的版本可能高于 0.34.0。新版本新增的工具默认需要确认，但已有工具的行为变化我们没有回归过。
  - **否决的做法**：
    - 跟随 stable 渠道自动升级：更新太频繁，又没有回归保障。
    - 要求版本严格等于 0.34.0、不等就提供"安装期望版本"：在 macOS 上等于降级全机共用的 App，会断开其他工具，还可能需要重新授权。
    - 装一份 DreamCoder 私有的 cua-driver：见设计文档"备选方案"。

## ADR-0002：只读工具放行，操作类工具逐次确认

- **状态**：已接受（2026-10-15），同日按源码对照审查修订
- **背景**：旧实现把 Computer Use 的工具全部放行，由 `request_access` 按应用逐个授权。这个授权弹窗不看会话的权限模式，"跳过权限"模式下也会弹。cua 没有这一层，每个工具都是直接执行的。
- **决定**：
  - 只读工具预先放行。只读工具指只读取屏幕、窗口、应用、会话和诊断信息、并且 cua 注解为 `readOnlyHint: true` 的工具，名单是常量 `CUA_READONLY_TOOLS`。
  - 其余工具都走现有的权限确认弹窗，可以选"本会话内始终允许"。这包括点击、输入、按键、拖拽、启动或结束应用、浏览器操作、写剪贴板、改配置、录制、安装扩展。
  - 读剪贴板、检查更新和检查权限也不放行：第一个涉及隐私，第二个会联网，第三个能弹系统授权框。
  - 新版本新增的工具默认需要确认。
  - 会话权限模式照常生效：在"跳过权限"模式下，所有 cua 工具都不确认；在 `dontAsk` 模式下，非只读工具被拒绝。Computer Use 开启时，切换到"跳过权限"模式会显示警告。
- **取舍**：
  - **好处**：模型观察界面时不会被频繁打断，真正动手前每次都要用户点头，安全边界清楚，而且复用现有的弹窗，不用新做界面。
  - **代价**：
    - 截图和窗口内容会在不经确认的情况下进入模型上下文。用户只要开启了 Computer Use，就等于默认允许模型"看"。这一点要写进设置页的说明。
    - "本会话内始终允许"按工具放行，不按应用。对"点击"选了始终允许，本会话里点击任何应用都不再询问，比旧实现的按应用授权宽。
    - "跳过权限"模式下没有任何确认，比旧实现少了一道按应用授权。我们选择尊重用户选的模式，只给出警告。
  - **否决的做法**：
    - 全部逐次确认：每一步都要点，体验太差。
    - 全部放行：模型可以在没有任何确认的情况下操作电脑。
    - "跳过权限"模式下仍强制确认 cua 工具：要在 CLI 的权限判断里给某个 MCP 服务开特例，和用户选的模式相矛盾，第一版不做。

## ADR-0003：不开启 cua-driver 遥测

- **状态**：已接受（2026-10-15），同日按源码对照审查修订
- **背景**：cua-driver 默认开启不含内容的产品遥测，数据发往 PostHog（欧盟节点）。DreamCoder 对外的说法是本地运行，隐私说明见 `PRIVACY.md`。
- **决定**：
  - **DreamCoder 安装的 cua-driver**：安装时带上 `CUA_TELEMETRY_ENABLED=0`，装好后执行 `cua-driver telemetry disable` 持久化关闭，并核对状态。
  - **每次启动 MCP 进程**：都带上 `DO_NOT_TRACK=1`、`CUA_TELEMETRY_ENABLED=0`，以及关闭更新检查的 `CUA_DRIVER_RS_UPDATE_CHECK=0`。
  - **用户自己已有的安装**：如果遥测是开启的，只在设置页提示并提供关闭按钮，不静默修改。
- **取舍**：
  - **好处**：和 DreamCoder 的隐私承诺一致。
  - **代价**：
    - cua 团队拿不到这部分使用数据。
    - 在 macOS 上，环境变量只作用于 `mcp` 代理进程，到不了由系统启动、全机共用的守护进程。对用户自己装的 cua，在用户点按钮之前，守护进程可能仍会发出遥测。
  - **否决的做法**：直接替用户修改已有安装的全局设置。原因是用户可能在别的工具里也在用 cua，自己做过选择。

## ADR-0004：Windows 上不注册登录自启任务

- **状态**：已接受（2026-10-15）
- **背景**：`install.ps1`（0.34.0）默认注册一个计划任务，每次登录时运行 `cua-driver serve`。这个任务以 `RunLevel=Highest`（管理员权限）运行，注册时会自行提权并弹出 UAC 对话框（约第 94–113、677–713 行）。安装器注释说没有守护进程时 MCP 调用会失败；但 `cua-driver manifest` 对 `mcp` 子命令的说明是"Windows/Linux 上直接在进程内运行"。
- **决定**：安装时传 `-NoAutoStart`。是否必须有守护进程，交给社区在 Windows 上实测。如果确实需要，改为会话需要时由 DreamCoder 启动一个非提权的 `cua-driver serve`，不注册开机任务。
- **取舍**：
  - **好处**：开启 Computer Use 不会弹 UAC，也不会留下一个每次登录都以管理员身份运行、能操作整个桌面的进程。
  - **代价**：
    - cua 用管理员权限是为了能完整读取 UWP 应用（计算器、新版设置、照片）的界面树；不提权时，这些应用的界面树可能只读到很少几个元素。
    - 如果实测证明 MCP 必须依赖守护进程，Windows 首个版本可能无法正常使用，需要追加实现。
  - **否决的做法**：保留默认行为，只在确认框里告知。这样用户为了一个可选功能，就要接受一个常驻的管理员进程。
