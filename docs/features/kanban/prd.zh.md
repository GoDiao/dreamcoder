**同日再补：审核人有自己的工作。** 指定审核人时带一段审核说明，写清怎么审（比如按某份规范审代码，或者协助人做验收）；没写就用默认说明。开新会话时可以直接让它当审核人。审核人接受时要写审核报告，负责人和创建者都会收到。任务处于 Review 时，看板上显示的是审核人。

**同日再补：取消由创建者决定。** 一张卡不需要了，由创建者判断，人可以替它决定。负责人觉得不需要时，标阻塞写明原因，由创建者处理。创建者是会话时，取消要人在会话里确认。取消时如果还有卡依赖它，或它还有没完成的子卡，系统列出这些卡，由取消的一方当场处理。

**2026-11-09 补：重新打开时通知负责人。** 人重新打开一张已完成或已取消的卡时，负责人收到通知，人可以顺手写一句原因。人写的原因往往说不清楚，所以负责人不要猜：原因不够清楚时，它把卡标为阻塞，把问题写在阻塞原因里，问题进人的 "待我处理"，人在卡上评论或者在它的会话里回答。取消时审核人也收到通知。

**同日再补：验收要点由创建者定。** 验收要点是创建者对结果的要求，负责人不再自己改。负责人觉得某条不清楚、不对或做不到时，去问创建者：创建者是会话就发消息问它，由它判断，需要人参与时它在自己的会话里问人；创建者是人就把卡标为阻塞写下问题，人从 "待我处理" 进负责人的会话，和它当面谈几轮定下来，再让它改，改动要人在那个会话里确认。验收要点在界面上一条一行编辑，不再是一整段文字；前面的标记改成圆点，因为看板不记录勾选。

**同日再补：审核人由创建者或人指定。** 审核人检查的是负责人的交付，所以负责人不能指定审核人，也不能开新会话当审核人；需要审核人时去找创建者。创建者和人可以把已有会话设为审核人，或者开新会话当审核人。会话把自己设为审核人，以及创建者同时是这张卡的负责人时指定审核人，每次都要人在会话里确认，不跟权限模式走。人取消卡片时，确认框已经列出受影响的卡，系统不再在取消后重复提示。

本文是产品需求，不规定存储结构和 agent 运行时的实现，这些留给技术设计。

## 一、产品定位

为 DreamCoder 已有的会话协作能力，加一块持久的项目看板，让人和 agent 围绕同一份任务状态协作。

看板记录**做什么、由谁负责、进展如何、结果是什么**。需求澄清、规划、实现、验证和协作，由 agent 自己在会话里完成。看板不把 agent 的工作过程改造成一套强制的工作流。

一句话：一棵任务和子任务组成的树，每张卡记着负责人、审核人和创建者，人和会话共用这块持久的看板。

## 二、要解决的问题

DreamCoder 的会话已经能新开其他会话、互相发消息、向父会话汇报。但是一件长期任务分给多个会话以后：

- 任务、负责人、依赖和进度散落在各个会话的聊天记录里，不容易追踪。
- agent 做完工作，结果和遗留问题不一定能可靠地沉淀到项目里。
- 人要挨个去问各个会话，才知道项目现状。
- 会话暂停或应用重启以后，项目层面的任务关系看不清。

本功能的价值：把长期的项目事实从对话里提取出来，并持续维护。它不重新实现一套 agent 执行环境。

## 三、角色与协作

### 角色

| 角色 | 作用 |
|---|---|
| 人 | 定义目标，决定谁来做，调整优先级，验收没有审核人的卡；能做看板上的任何操作 |
| 负责人 | 做这张卡：维护进度，报告阻塞和结果。任务大时把它拆成子卡 |
| 审核人（可选） | 按审核说明检查这张卡的交付（看代码、跑测试、协助人验收等），写审核报告确认完成，或者退回 |
| 创建者 | 建这张卡的人或会话：管理这张卡，收到它的阻塞和提交 |

同一个项目里的会话都能看到整块看板。

### 约定

（2026-11-07 修订：去掉 PM 和上下级，原来的 Lead 和 Worker 也已合并为 "负责人"。）

1. **没有项目级的 PM，也没有上级。** 卡片之间只有任务和子任务的关系。规划和拆分由人来做，或者由人请某个会话来做。
2. **负责人、审核人和创建者是会话和某张卡之间的关系，不是会话的固定身份。** 同一个会话可以负责一张卡，同时审核另一张卡。
3. **负责人可以拆自己的卡。** 拆出来的子卡，创建者就是这个负责人。它可以为子卡分配负责人和审核人；需要检查子卡的结果时，把自己设为子卡的审核人，这要人确认。拆不拆由负责人自己判断，层数不限。
4. **会话的分配要人同意。** 卡的创建者和负责人可以把卡分配给其他会话当负责人；审核人只由创建者和人指定。任何会话都可以把自己设为某张卡的负责人或审核人。分配在会话里弹确认卡片，跟着会话的权限模式走；分配给自己开出来的子会话不再确认。会话把自己设为审核人，或者创建者兼负责人指定审核人时，每次都确认，不跟权限模式走。开新会话来做或审一张卡时，开会话的确认卡上写明它负责或审核哪张卡，确认一次就够了。
5. **在别处建卡要人同意。** 会话在自己负责或自己建的卡下面建子卡，直接建出；在别处建卡（包括顶层的卡）算作建议，在会话里弹确认卡片。
6. **卡片树和会话树不要求一致。** 卡片树表达工作的拆分；会话树表达谁新开了谁。负责人常会自己新开子会话来做子卡，但已有的会话也可以被分配到任务上。

### 每张卡的三种身份

| 身份 | 是谁 | 做什么 |
|---|---|---|
| 负责人 | 最多一个会话 | 开始、更新进度、提交交付报告 |
| 审核人 | 最多一个会话，可以没有 | 检查交付，确认完成或者退回。没有审核人时由人验收 |
| 创建者 | 建这张卡的人或会话 | 管理这张卡的状态和分配，收到它的阻塞和提交 |

- 同一张卡的负责人和审核人不能是同一个会话，所以一个会话不能验收自己的交付。人随时可以替代审核人做决定。
- 这些身份只看卡片本身。父卡换了负责人，子卡的负责人、审核人和创建者都不变。
- 例子：

```text
T1 认证系统重构        创建者 人   负责人 A   审核人 无（人验收）
└── T2 OAuth 模块      创建者 A    负责人 B   审核人 A
    └── T3 Token 服务  创建者 B    负责人 C   审核人 无（人验收）
```

## 四、核心概念

不规定存储结构，产品上只需要这些概念：

- **项目看板**：一个项目一块，关联项目根目录。
- **任务卡**：编号、标题、描述、验收要点、状态、优先级、负责人、审核人、创建者、父卡、时间信息。
- **依赖**：卡片之间 "必须先完成" 的关系，用来显示等待关系和是否就绪。
- **指派**：卡片和负责人、审核人会话之间的关联，记录谁分配的、什么时候生效或撤下。
- **更新和评论**：进度说明、遇到的问题、讨论结论、关键决定。
- **交付报告**（2026-11-07 修订）：负责人提交的结果报告，写做了什么、怎么验证的、还有什么没解决，按 Markdown 显示；可以附分支、提交、PR 或文件的链接作为参考。做出来的东西本身（代码、分支、文档）留在原处，不存在看板上。

项目卡片是长期任务的唯一可信来源。会话内部的待办清单（现有的 TaskCreate、TaskUpdate 等）仍然可以用来记录 agent 自己的执行步骤，不需要和项目卡片一一对应。

## 五、工作流程

### A. 简单任务

1. 人建卡，或者会话建议一张卡、人同意。卡上写清目标和可以检查的完成条件。
2. 人把任务分给一个已有的或新开的会话作为负责人；会话也可以分配，在会话里确认。需要时再指定审核人。
3. 分配生效后，负责人会话收到一条通知，里面有卡片编号和任务摘要；它通过看板工具读取完整的任务。
4. 负责人开始工作，在卡上更新进度或阻塞原因。
5. 负责人提交交付报告，卡片进入 Review。审核人和创建者收到通知。
6. 审核人按审核说明检查后，写审核报告确认完成，或者退回；没有审核人时由人验收。负责人和创建者收到确认完成的通知。

### B. 复杂任务：负责人拆分

1. 人建一张粗粒度的任务卡，分配给一个负责人。负责人会话收到分配通知。
2. 负责人开始工作。它可以先在自己的会话里和人多轮澄清需求、调查代码、讨论方向。
3. 负责人把讨论的结论写回卡片：描述、评论和关键决定；验收要点要改时找创建者（见 R42）。判断需要拆分时直接拆出子卡，建立依赖。
4. 负责人开新会话来做子卡，开会话的确认卡上写明新会话负责哪张子卡，人确认一次，新会话一启动就是负责人；也可以把子卡分配给已有的会话。需要检查子卡结果时，负责人把自己设为子卡的审核人，人确认。子卡的负责人还可以继续拆分。
5. 子卡阻塞或提交时，作为创建者的负责人收到通知。它处理阻塞，并以审核人的身份验收子卡。
6. 子卡完成后，负责人汇总结果，提交父卡的交付。子卡全部完成，不会自动把父卡设为完成。
7. 父卡的审核人检查整体交付，确认完成；没有审核人时由人验收。

需求澄清本身是工作过程的一部分：负责人可以在 "进行中" 的状态下不断完善卡片内容，不需要单独的需求状态、版本审批和重开流程。重要的需求变更要写成一条更新记录，并通知受影响的子卡负责人。

### C. agent 发现额外工作

agent 在自己负责或自己建的卡下面，可以直接建子卡。在别处建卡（顶层的卡，或者别人的卡下面）算作建议：会话里弹出确认卡片，显示标题和描述。

- **同意：** 卡片正式建出来，建议它的会话成为创建者。
- **拒绝：** 看板上什么都不留。

这个确认跟着会话的权限模式走：跳过确认的模式下直接建出，人也可以在卡片上选择 "本会话都允许"。建出来的卡没有负责人就不能开始，所以谁来做仍然由人决定。

不新增 "提议" 状态，看板上也不保留待决定的建议。会话做的分配也一样：在会话里确认，看板上不留待确认的分配。

## 六、状态与权限

### 状态

| 状态 | 含义 |
|---|---|
| Backlog | 已记录，还没准备执行，或者暂时搁置 |
| Todo | 任务明确，等待分配或开始 |
| In Progress | 负责人正在工作，包括调研和需求澄清 |
| Blocked | 当前无法推进，必须写明原因 |
| Review | 已提交结果，等待检查和验收 |
| Done | 交付已确认 |
| Cancelled | 不再执行，保留历史 |

- 依赖还没满足的卡，显示为 "等待依赖"，不需要改成 Blocked；这时服务端拒绝开始这张卡。
- 卡片详情里显示子卡、依赖、负责人、审核人、创建者、状态、最新进展和交付报告。

### 谁能做哪些转换

服务端只校验最基本的身份和操作权限，不做多阶段的工作流引擎。

| 操作 | 谁能做 |
|---|---|
| 在 Backlog 和 Todo 之间移动、排序 | 创建者、人 |
| 编辑标题、描述、优先级和依赖 | 负责人、创建者、人 |
| 修改验收要点 | 创建者、人；负责人改要人在它的会话里确认（R42） |
| 开始：Backlog 或 Todo → In Progress | 负责人；分配已生效，且依赖的卡都已完成 |
| 标阻塞（写原因），解除阻塞 | 负责人、创建者、人 |
| 提交结果：In Progress → Review | 负责人，必须附交付报告 |
| 要求修改：Review → In Progress | 审核人、人 |
| 确认完成：Review → Done，附审核报告 | 审核人、人；没有审核人时只有人 |
| 重排或换人：In Progress → Todo | 创建者、人 |
| 取消（会话取消时要人确认），撤销分配 | 创建者、人 |
| 把卡分配给其他会话当负责人 | 负责人、创建者、人 |
| 指定审核人（已有会话或新开会话） | 创建者、人；创建者同时是负责人时要人确认 |
| 把自己设为负责人或审核人 | 任何会话、人；设为审核人要人确认 |
| 重新打开已完成或已取消的卡，归档 | 人 |

人在看板上拖拽卡片，可以做表中的任何操作。agent 只能通过看板工具操作，并受这张表约束。会话做的分配在会话里弹确认卡片，跟着会话的权限模式走；分配给自己开出来的子会话时不弹。会话把自己设为审核人，或者创建者兼负责人指定审核人时，确认卡片每次都弹。

## 七、首版功能需求

### 7.1 持久的项目看板

- **R01** 一个项目对应一块持久的看板。从同一个项目的不同分支或 worktree 进入，看到的是同一份任务数据。
- **R02** 支持卡片的创建、编辑、取消和归档，以及排序、设置优先级、拖拽改状态。拖拽受第六节的权限约束。
- **R03** 支持子卡拆分，层数不限；支持 "必须先完成" 的依赖，并拒绝会形成循环的依赖。
- **R04** 卡片记录描述、验收要点、评论、进度更新和结果链接，应用重启后仍然可以查看。
- **R05**（2026-11-07 修订，2026-11-09 再修订）卡片的验收要点由创建者和人设定和修改，审核人或人据此验收。负责人不自己改要点，见 R42。
- **R42**（2026-11-09 补）负责人觉得某条验收要点不清楚、不对或做不到时，向创建者提出。创建者是会话时，负责人发消息给它，由它决定改或不改并回复负责人；需要人参与时，创建者在自己的会话里先问人。创建者是人时，负责人把卡标为阻塞并写下问题；"待我处理" 里这一条可以直接打开负责人的会话，人和它谈定后，可以让它改要点，每次改动都要人在那个会话里确认，确认时列出新增和删除的要点。
- **R31**（2026-11-07 修订）人可以从项目菜单建看板。项目还没有看板时，会话建第一张卡会连同看板一起建立，这时总要人确认，和会话的权限模式无关。
- **R33**（2026-11-07 补）卡片上的文字（进度、提交摘要、退回意见、阻塞原因等）保持简短，超过上限时系统拒绝并提示改写成文件。较长的内容（比如 review 报告）写成项目里的文件，在提交或退回时作为链接附上。人在卡片详情里点开链接就能在侧边面板查看文件，agent 需要细节时读取文件。agent 读卡时默认只拿到最近的进度和最近一次交付，需要时再取完整记录。

### 7.2 分配与权限

- **R06**（2026-11-07 修订）看板不关联固定的 PM，卡片之间也没有上下级。每张卡的负责人、审核人和创建者记在卡片本身上，父卡的变化不影响子卡的这些身份。
- **R07**（2026-11-07 修订）负责人可以把自己的卡拆成子卡，不需要确认，层数不限。它是子卡的创建者，可以为子卡分配负责人和审核人。
- **R08**（2026-11-07 修订）人可以把卡直接分配给已有的会话或新开的会话；人分配的新会话挂在卡的创建者会话下面，卡由人建的就单独开。卡的创建者和负责人可以把卡分配给其他已有的会话当负责人，审核人只由创建者和人指定（见 R43），任何会话可以把自己设为负责人或审核人；这些分配在会话里弹确认卡片，跟着会话的权限模式走。分配给自己开出来的子会话时不弹，开这个会话时人已经同意过。分配一个已有人担任的位置时，原来的会话被撤下并收到通知。
- **R34**（2026-11-07 补，2026-11-08 修订，2026-11-09 再修订）卡的创建者和负责人开新会话时可以指定它负责这张卡，创建者还可以指定它审核这张卡。开会话的确认卡上写明是哪张卡、什么身份，人确认后新会话一启动就担任这个身份，原来担任的会话被撤下。新会话挂在开它的会话下面。开审核人时，开场任务就是它的审核说明。
- **R35**（2026-11-08 补）指定审核人时可以写一段审核说明：审什么、按什么标准，比如审代码或者协助人验收。没写时用系统的默认说明：等负责人提交，对照每条验收要点检查交付，查完写报告接受或者退回。审核说明出现在审核人收到的分配通知、负责人提交后的通知（同时附上验收要点）和卡片详情里。
- **R36**（2026-11-08 补）审核人或人确认完成时必须写审核报告：查了什么、怎么查的，可以附文件链接。报告记在卡上，负责人和创建者收到通知。
- **R37**（2026-11-08 补）卡片处于 Review 且有审核人时，看板、层级视图和卡片详情显示审核人和它是否在运行，而不是负责人。
- **R09** 分配生效后，被分配的会话收到一条通知，并能通过看板工具读取完整的任务。通知的基本信息由系统根据卡片生成：卡片编号、标题、任务摘要、验收要点、创建者，以及由谁验收；分配的一方可以补充一段说明。人分配的新会话以这条通知作为第一条消息；会话开新会话来做或审一张卡时，它写的开场任务作为这次分配的说明，和这些信息一起作为新会话的第一条消息。已有会话没有在运行时，通知会让它恢复运行并收到。
- **R10** 分配被撤销或换人时，原来的会话收到通知，之后不能再更新这张卡的执行结果。
- **R38**（2026-11-08 补）只有卡的创建者和人能取消卡。创建者是会话时，取消在会话里弹确认卡片，人同意后才生效。
- **R39**（2026-11-08 补）负责人认为卡不需要时，不能自己取消；它把卡标为阻塞并写明原因，由创建者决定取消还是继续。
- **R40**（2026-11-08 补）取消一张卡时，如果有没完成的卡依赖它，或它还有没完成的子卡，系统列出这些卡：会话取消时写在结果里，人在看板上取消时写在确认框里。取消的一方当场决定删掉这些依赖，或者把这些卡一起取消。
- **R41**（2026-11-09 补）人重新打开一张已完成或已取消的卡时，可以写一句原因（可选），负责人收到通知。原因不够清楚时，负责人把卡标为阻塞，在阻塞原因里写下它的问题，由人在卡上评论或在它的会话里回答，弄清楚后再解除阻塞。
- **R32**（2026-11-07 补，2026-11-09 修订：取消时审核人也收到通知）卡片被退回修改、解除阻塞、退回待办或取消时，负责人收到通知，通知里带操作者和原因；退回修改时还带附上的文件链接。负责人自己做的操作不通知自己。
- **R11** 一张卡同时最多一个负责人、一个审核人。
- **R43**（2026-11-09 补）审核人只由卡的创建者或人指定，负责人不能指定审核人。会话把自己设为审核人时，以及创建者同时是这张卡的负责人而指定审核人时，每次都要人在会话里确认，不跟权限模式走。
- **R12** 负责人只能开始和更新自己负责的卡，不能处理其他会话的任务。只有当前的负责人能提交这张卡的执行结果。
- **R13**（2026-11-07 修订）同一项目的会话都能看到整块看板。修改权限按第六节的表：负责人、审核人和创建者各自能做的操作不同，人能做全部。
- **R14** 审核人不能和它审核的卡的负责人是同一个会话。验收由审核人做，所以会话不能验收自己的交付。
- **R15**（2026-11-07 删除）原来要求负责人和验收方不是同一个会话。验收方并入审核人以后，由 R14 保证。

### 7.3 agent 的进度与协作

- **R16** agent 通过看板工具：查询任务、查看依赖、开始任务、更新进度、标记阻塞、提交结果、建卡或建议新卡、分配。
- **R17**（2026-11-07 修订）负责人通过看板工具：拆分子卡、查看子卡进度、收到子卡的阻塞和提交、以审核人的身份验收子卡、汇总父卡的交付。
- **R18** 卡片的每次改动都保留操作历史：时间、操作者（人或哪个会话）、改了什么。
- **R19**（2026-11-07 修订）任务汇报保存到对应的卡上。提交时通知审核人和创建者，阻塞时通知创建者，通过现有的会话消息送达，不依赖会话的父子关系。
- **R20** 会话暂停、关闭或应用重启后，看板和角色关联保持不变；会话重新打开后，能继续查询自己的任务。
- **R21** 卡片上显示负责人的会话是否正在运行。运行状态和任务状态分开显示，不互相替代。
- **R22** 负责人提交父卡的结果时，如果还有没完成的子卡，系统给出提示，但不阻止提交。

### 7.4 人的操作与轻量验收

- **R23** 人可以查看完整的看板，修改优先级和分配，检查所有 agent 的进度和交付。
- **R24**（2026-11-07 修订）提供一个简洁的 "待我处理" 入口，至少包含：没有审核人（或审核人会话已删除）的交付、阻塞的卡、负责人空缺的卡。
- **R25**（2026-11-07 修订）会话在别处建卡时，在会话里弹确认卡片；人同意后卡片建出，拒绝则不留记录。这个确认跟着会话的权限模式走。看板上不保留待决定的建议。
- **R26**（2026-11-07 修订）负责人可以把卡提交到 Review；审核人或人可以确认完成（附审核报告，见 R36），或者退回；没有审核人时由人验收。
- **R27** agent 提交结果不会直接让卡片变成完成。
- **R28** 从卡片详情可以打开关联的会话，方便人继续澄清需求、追问进展或要求修改。
- **R29**（2026-11-07 修订）人在卡片上评论时，评论默认送到负责人的会话。人可以选择同时送给这张卡的创建者。agent 的评论只记在卡上，不唤醒其他会话。
- **R30** 负责人的会话被删除时，卡片保留，负责人显示为空缺，并列入 "待我处理"，由人重新分配。

## 八、页面与交互

首版只做一块看板、一张卡片详情和一个 "待我处理" 入口，不做完整的项目管理套件。

- **看板**：按状态分列，可以拖拽。卡片上显示子卡数量、负责人、优先级、阻塞标记、是否在运行、最近更新时间。
- **层级（2026-11-07 补，2026-11-09 修订）**：同一份数据的另一种看法，按父子关系展开卡片树，并标出依赖。原来的 "分工" 视图（按会话列出它负责和审核的卡）已删除：每张卡只记负责人、审核人和创建者以后，它和看板的负责人筛选重复。
- **卡片详情**：目标、验收要点、子卡、依赖、讨论和进度、交付报告，以及负责人、审核人（没有时显示由你验收）和创建者；审核人下面显示审核说明。详情在右侧面板里打开，看板和会话里都能打开，不离开当前页面。
- **待我处理**：待人验收的交付、阻塞的卡、负责人空缺的卡。
- **和会话联动**：从卡片打开会话。界面和 agent 的工具读写同一份数据。会话建议的卡和会话做的分配都在会话里确认。

## 九、非目标

首版不做：

- 独立的需求状态、需求版本、强制的需求确认流程。需求靠会话澄清，结论写在卡片上。
- 评审、验收、合并分阶段的强制流程；评审轮次上限；完整的审批引擎；自动批准分配的开关。
- 项目级的 PM、沿卡片树推出的上下级、委派层数限制、按身份限制会话能看到哪些卡。
- 自动创建或切换卡片专属的 worktree，集成分支管理，自动的合并、变基或 PR 流程。分支和 PR 只作为交付报告里的参考链接记录在卡上，由 agent 用现有的 Git 能力处理。
- 预测文件修改范围、按文件冲突调度、由服务端阻止文件重叠。
- 自动调度就绪任务、Worker 池、失败重试、租约、agent 自主排程。
- 每张卡的花费统计、跨项目总看板、定时生成卡片、复杂的通知规则。
- 多用户、云端同步、可配置的工作流、甘特图。

这些能力以后可以作为独立的增强。现有会话和 Git 能力已经产生的结果，看板只做关联，不重复实现。

## 十、验收标准

产品是否可用，以完整的用户旅程来验证，不看实现了多少配置项。

1. 人为项目建立看板，或者会话建第一张卡时经人确认建立。关闭再打开应用后，任务都还在。
2. 人建一个复杂任务并指派负责人。负责人能在自己的会话里澄清需求、更新卡片，直接拆出子卡。
3. 人或负责人把子卡分配给其他会话。子卡负责人收到带卡片编号和任务摘要的通知，能通过工具读取并开始自己的任务，但不能处理不归它的任务。已有会话和新开会话都要验证；负责人开新会话做子卡时，人只确认一次，新会话启动时已经是负责人。
4. 子卡负责人能报告进度、阻塞和完成结果。拆出子卡的负责人能在看板上看到子卡的进度，并收到子卡的阻塞和提交。这包括子卡负责人不是它新开的会话的情况。
5. 审核人或人能检查交付、要求修改、确认完成；没有审核人的卡由人验收。父卡不会因为子卡全部完成而自动完成。agent 不能把自己的卡直接改成完成，也不能验收自己的交付。
6. 会话在别处建卡时，人在会话里确认；跳过确认的权限模式下直接建出。父卡换负责人后，子卡的负责人、审核人和创建者不变。
7. 应用重启后，任务状态、层级、分配、评论和交付报告都能恢复；没有 agent 在运行时，看板也能正常使用。

## 十一、留给技术设计

产品层面的问题都已确认。以下留给技术设计决定：

- 看板用哪种本地存储，怎样保证并发更新不丢数据。
- 项目和它的多个 worktree 怎样对应到同一块看板。
- 看板工具怎样和现有的会话工具、消息机制衔接。
- 分配通知怎样送达已有会话和新开会话（复用现有的会话消息），以及角色变更怎样生效。
