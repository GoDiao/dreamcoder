# agent 运行时与框架全景

核实日期：2026-10-23。范围：多 agent 编码团队里「成员如何被启动、承载、隔离、恢复与卸载」这一层，以及这一层提供的多 agent 原语（交接、派生、消息、共享状态）。上层产品见 [README](../README.md)，同层的持久化与调度见 [landscape-orchestration.md](landscape-orchestration.md)，工作区与沙箱见 [landscape-workspace.md](landscape-workspace.md)。背景讨论见 [#162](https://github.com/GoDiao/dreamcoder/issues/162)。

## 0. 读法与核实约定

- 本次只读：没有安装、构建或运行任何被调研的框架；GitHub 只用 `gh api` 读接口，网页只读。
- 「许可证」「仓库创建」「最新 release 与日期」除特别标注外，均来自对应仓库的 GitHub API（`gh api repos/<owner>/<repo>` 与 `.../releases/latest`，2026-10-23 读取）。表格里的名称链接即该仓库或文档入口，不在每格重复。仓库创建日不等于首次发布，只作成熟度的下限参考。monorepo 的 latest release 标签只对应其中某个包，已在格内注明，不能当作框架整体版本。
- GitHub 判定为 NOASSERTION 或空的许可证，写明读到的实际文本或「未核实」。
- 「未查到」表示查过但没有证据；「不适用」表示问题本身不适用。
- 每个框架回答同样五个问题：能否混用多个 provider；能否把外部 CLI 包成成员；有无持久化与恢复；人如何和成员对话；能否跑在 Bun 或 Node 里、嵌进桌面应用。没有证据的写「未查到」，不凭印象补。
- 表中「使用方」只写能给出出处的集成，包括框架之间互相包装的包；没有出处的不写。
- 判断与建议只出现在「适配」列和文末两节里。
- 我们当前的运行时（所有成员在同一个 CLI 进程内，见 [#162](https://github.com/GoDiao/dreamcoder/issues/162) 的「What DreamCoder has today」）作为对照放在 1.1 的第一行，其中 fork 的行为没有重读源码，以 #162 的描述为准。

### 1.2 小结

- 厂商 SDK 分两类：自带循环的（Claude Agent SDK、OpenAI Agents SDK、ADK、Strands、MAF），和包装外部 CLI 的（Codex SDK、OpenCode SDK、ACP、已归档的 agentapi）。前一类里只有 Claude Agent SDK 的「循环」就是 Claude Code 本体，也就是我们已经在用的东西。
- 「多 provider」在自带循环的框架里是常态（OpenAI Agents SDK 的 `ModelProvider`、MAF 的各 provider 包、Strands）；而 Claude Agent SDK 的子 agent 只有 `model` 字段。#162 已写明 in-process 成员不能换 provider，这与 SDK 的表面一致。
- 人工介入的主流形态是「暂停、返回待审批项、稍后凭可序列化状态恢复」（OpenAI 的 `RunState`、Claude SDK 的 `canUseTool`），不是自由对话。允许人在成员运行中途直接发消息的，本次只在 Claude Code 的 in-process teammate 面板和 OpenCode 的 `noReply` 注入里见到。
- 恢复粒度各不相同：Claude 与 Codex 把会话存成本机文件，OpenAI 序列化 `RunState`，ADK 与 LangGraph 一类走数据库；没有一个框架把「恢复」扩到团队级别（邮箱、任务列表、成员关系），Claude Code 自己的文档也承认 in-process teammate 不会被 `/resume` 还原。

### 2.2 小结

- 对「成员是外部 CLI」这一需求，目前有三条并行路线：ACP 协议加适配器（Mastra `@mastra/acp`、Vercel `harness-acp`）、各厂商 SDK 的进程包装（Codex SDK、Claude Agent SDK，及被 Mastra、Vercel、MAF 再包一层）、已弃用的终端屏幕解析（agentapi）。
- 两个 TS 框架已经把「包装 CLI」做成一等公民：Mastra 的 `agent-sdks/` 和 Vercel 的 `harness-*`。两者的接口都是「一次 prompt、一个流式响应」，团队级概念（共享任务、邮箱、成员关系）不在它们的接口里；本次读到的文档与 README 中没有这些词。
- Vercel Harness 是唯一在接口层写出「暂停一轮、序列化、稍后接续」的方案，且把它与持久化工作流（Workflow DevKit）接上了；代价是真实沙箱目前只有 Vercel 托管实现。
- Python 与 .NET 的框架（CrewAI、AG2、Pydantic AI、smolagents、MAF）无法直接嵌进 Bun 或 Node 宿主，只能当外部服务或借鉴设计。
- 「厂商 SDK 与封装层」「通用框架」两节都没有给出 Windows 上的本机沙箱：OpenAI 的本机沙箱客户端在 Windows 上要换 Docker 或托管，Vercel 的真实沙箱是托管的，ACP 协议不涉及沙箱。

## 3. 值得深拆的候选

下面只写意见，按推荐顺序，均按 [_template.md](_template.md) 的格式做完整拆解。

1. Vercel AI SDK Harness（`@ai-sdk/harness` 与 `harness-claude-code`、`harness-acp`、`workflow-harness`）。它是唯一把「异构 CLI 成员」「暂停与接续一轮」「持久化工作流」放进同一套接口的方案，正对应 #162 里「空闲成员是否卸载与恢复」「进程成员与 in-process 成员如何合成一个团队」两个问题。要查的是宿主模式适配器能否脱离 Vercel 沙箱在本机跑，以及状态负载有多大。
2. Mastra（重点是 `agent-sdks/claude`、`agent-sdks/acp`、libSQL 存储与挂起恢复）。TS 栈里同时具备多 provider、CLI 包装与 SQLite 的只有它；还能让工作流跑在 Inngest 或 Temporal 上（见编排文件）。要查包装后丢失的控制（权限、工具）和 `ee/` 目录的许可边界。
3. Claude Agent SDK（含 `SessionStore`、子 agent 恢复、`canUseTool`、`bun build --compile` 的处理）。它与 DreamCoder 驱动 CLI 的方式同源，拆解的目的是对照 fork 的差异：上游文档称 SDK 会话不派生 teammate，而 fork 在 `--print` 下强制 in-process；还要核对商业条款对「第三方登录」的限制。
4. ACP 与 `claude-agent-acp`、`codex-acp`。如果走「一成员一进程」，ACP 是覆盖 agent 最多的接入协议。要查 `session/load` 是否被 Claude 适配器实现，`session/request_permission` 能否映射成我们的权限请求（对照 #164），以及协议没写的并发多会话。
5. OpenAI Agents SDK（JS）的 `RunState` 序列化与审批中断模型，以及它的 Sandbox Agents。作为「暂停与恢复」的小而完整的参照实现，可借鉴语义，不一定采用代码。
6. LangGraph.js 的检查点与 `interrupt()` 语义，附带 `checkpoint-sqlite` 在 Bun 与 Tauri 打包下的可用性。作为「恢复时节点从头重跑」这一约束如何影响设计的参照。

没有列入的：AutoGen（已归档）、agentapi（已弃用）、CrewAI、smolagents、Pydantic AI、AG2（均为 Python，不能嵌入；Pydantic AI 的持久化引擎清单已记入编排文件）、Google ADK（provider 面窄）、Strands（本次没找到切入点）、VoltAgent（被 Mastra 覆盖）。

## 4. 空白

按我们的需求逐项列出，目前没有找到做得好的现成方案：

1. 团队级语义的运行时：共享任务列表、邮箱、成员名册、lead 与 teammate 的关系。本次读到的框架接口里都没有这些概念，Claude Code 自己的实现也被其文档列为实验功能并承认不可恢复。
2. 同一进程里混用 provider 的成员：Claude Agent SDK 只有 `model` 字段；自带循环的框架能混用，但丢掉 Claude Code 的工具与权限体系。包装 CLI 的方案能保留工具，却是一成员一进程。
3. 成员的卸载与恢复（类似 Codex 的做法）：只有 Vercel Harness 在接口层写了；其余要么只存会话文本（Claude、Codex），要么只存图状态（LangGraph、Mastra），没有包含「邮箱与任务」的团队级恢复。
4. 人在成员运行中途直接发消息：框架的人工介入基本是「暂停等待审批」；OpenCode 的 `noReply` 注入和 Claude Code 的 in-process 面板是仅有的两个例子，本次没有找到把它做成通用接口的框架。
5. Windows 上包装 CLI 成员并带本机沙箱：OpenAI 的本机沙箱客户端 Windows 不可用，Vercel 的真实沙箱是托管的，ACP 不管沙箱。
6. Bun 宿主的兼容性证据：只有 OpenAI Agents JS 的 README 明确列出 Bun；Claude Agent SDK 的 `executable` 选项含 `bun`；其余 TS 框架本次未查到明说。
7. 本次未覆盖：LangChain 之外的 Deep Agents、Semantic Kernel、Genkit、BeeAI、AgentScope 等；以及 Anthropic 的 Managed Agents（托管形态，与本地优先定位不合，仅在 SDK 概览页见到）。
